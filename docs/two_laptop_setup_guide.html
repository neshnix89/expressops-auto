Why both machines can run the same task

  • A run lock. Before writing anything, each task creates a lock file in the shared folder. One machine wins; the other writes "the other laptop is covering it" in its log and stops. A lock left behind by a laptop that was closed mid-run is taken over after 20 minutes, so nothing can jam permanently.
  • Shared state. The MO monitor's history and alert queue, and the costing baseline, all live on the Y: drive rather than on either laptop.
  • JIRA as the shared record. The costing task recognises its own hidden footers in the comments, which both machines can see.
  • If the Y: drive is unreachable, tasks run anyway and say so in the log. A missed report is worse than a rare duplicate, and a machine that cannot see the share cannot coordinate with the other one in any case.

Daily check while covering

Get-ScheduledTask | Where-Object { $_.TaskName -match 'KPI|MR|Costing|MO_Ref' } |
  ForEach-Object { $i = Get-ScheduledTaskInfo $_.TaskName
    "{0,-24} last={1} result={2}" -f $_.TaskName, $i.LastRunTime, $i.LastTaskResult }

result=0 means success. Logs are in the logs\ folder.

For the MO monitor, attempt 1: MATCH in mo_ref_order_monitor_run.log means Webex delivery is healthy. Repeated attempt 2 or attempt 3 means that laptop is slow to switch Webex spaces — raise open_delay_seconds in its config.yaml from 6 to 10.

If anything ever looks wrong

JIRA is the source of truth, not Webex. If an alert seems to be missing, check the Work Container before assuming the MO has not moved.
